HP Making Batch Management Tool

一个面向洗护制造场景的批次智能辅助决策工具。系统结合多源计划数据、产线与机组约束、双层容差控制、局部评分排序与可解释输出，帮助计划团队在复杂的 MOQ 与班次容量约束下形成更稳定、更透明的搅拌批次方案。

1. 工具价值与应用场景

该工具用于支持 HP 洗发水、护发素生产计划的批次生成、搅拌系统分配、超限识别与过程解释。

多源数据整合ZCPRS / ZC228 / Parameter / Making Capacity / Conversion List
多层规则控制WIP、班次、产线、系统、MOQ、白名单
局部智能决策可行组合筛选 + 系统候选评分
报表可解释Orders / Batches / Alerts / Decision Explain

2. 数据源与主数据结构

工具以生产计划主表为核心，结合产品参数、搅拌能力与半批白名单形成完整决策链。

数据源核心字段业务作用

3. 核心计算逻辑

系统围绕班次、目标 MOQ、容差区间与物理批次数进行层层判断。

班次计算：
N = 00:00–07:59，D = 08:00–15:59，M = 16:00–23:59
评分元组：
Score = (overflow, gss12_small, priority, usage, closest, system_name)
  • overflow：是否超该日期该班次上限
  • gss12_small：GSS1+GSS2 做 2.2 小批的惩罚
  • priority：系统优先级，GSS1+GSS2 < GSS3 < GSS4
  • usage：该日期该班次当前已占用的物理批次数
  • closest：系统能力与目标规格的贴近程度
说明：当前工具不是全局最优求解器，而是“规则筛选 + 启发式组合 + 局部评分排序”的混合决策模式。

4. 双层容差机制

Preferred 用于优选，Hard 用于兜底可行性控制；多个 4.4 MOQ 的目标会按批次数放大容差。

TargetPreferred 区间Hard 区间说明
2.22.12 ~ 2.281.90 ~ 2.50标准小批区间
4.44.28 ~ 4.524.10 ~ 4.70标准主批区间
11.010.76 ~ 11.2410.30 ~ 11.703批场景，容差相对单批放大
简化案例：订单 2998987389，Load = 11.489，Batch Count = 3。
旧逻辑容易误把目标看成 13.2；当前逻辑会更合理地识别为 Target = 11.0，并给出：
Preferred = [10.760, 11.240]，Hard = [10.300, 11.700]。
因为 11.489 高于 Preferred，但仍低于 Hard 上界，所以属于“可接受但非最优”的多批次命中。

5. 组合判断逻辑

系统先判断能不能搭，再判断搭好以后该给哪个系统，体现“规则优先、评分辅助”的思想。

Step 1：按 WIP 分组

只有相同 WIP 的订单才会进入同一批次规划池。

Step 2：小单多订单组合 + 大目标优先

小单优先通过多订单组合（2、3 甚至更多）尝试 4.4 / 2.2 标准 MOQ 搭批；普通单按目标从大到小降序尝试，优先合成更大批次。

Step 3：先同日、再跨日

满足业务窗口才允许进入搭批候选集合。

Step 4：合法系统评分排序

多个系统都可行时，才用评分元组决定最终系统。

Step 5：二次合并（可开关）

首轮分配后，若发现“欠装单批 + 同WIP同系统”可升级到更高合法目标（如17.6），执行 Second Pass Merge。

Step 6：超限再平衡

二次合并后再执行系统借产能（如 GSS3 超限回退到 GSS1+GSS2），并重建日期+班次占用。

关键理解：“是否能搭批”主要靠规则判断；“搭好了以后选哪个系统”才主要靠打分。

5.1 新增运行逻辑（Second Pass Merge）

该流程用于修复“理论可大批、首轮未合并”的场景，同时保证不破坏原有班次与产能规则。

运行顺序：
首轮搭批与系统分配 → 二次合并（可开关）→ 超限再平衡 → 班次重汇总 → 输出报表
阶段判断条件输出结果
候选筛选 同系统 + 同WIP + 同产品类型；至少一侧为欠装单批（Load/Target < 0.90） 得到可尝试合并的批次对
目标选择 合并后总载荷可命中合法 MOQ 目标（硬容差内），且系统支持该目标 生成合并后的新目标批量（如 17.6）
保护校验 不允许任何系统-日期-班次的超限程度恶化；避免健康批次连环放大 只保留“修复型合并”
重汇总 按订单的日期+班次分摊 batch_count，再重建班次占用 Orders / Batches / Alerts 口径一致
例子：3019518253(3.538) + 2990748521(13.821)
首轮可能拆成两个批次；二次合并会将其升级为同一批次目标 17.6，并在后续再平衡阶段检查班次上限风险。

7. 算法架构说明

当前工具不是单一算法模型，而是“规则引擎 + 启发式搭批 + 局部组合搜索 + 多指标评分排序”的混合决策架构。

Rule Engine

先做约束过滤：同 WIP、产品类型匹配、产线限制、时间窗限制、白名单限制、班次容量限制。只有通过这些规则的订单才会进入下一步。

Heuristic Batch Formation

采用启发式与贪心逻辑进行组批，优先尝试标准 MOQ（如 4.4 / 2.2），先同日，再跨日，而不是对全量组合做全局穷举。

Local Combinational Search

在余量拆分和目标贴近环节，使用局部 DFS 组合搜索，寻找最接近目标规格的尺寸组合，例如 4.4 + 2.2、4.4 + 4.4 + 2.2 等。

Multi-Criteria Ranking

当多个系统都合法时，使用评分元组做词典序排序，从而选出更适合的 GSS 系统，而不是仅靠固定优先级。

决策逻辑可以概括为：
先判断能不能搭批 → 再判断目标 MOQ 是否可接受 → 最后在合法系统之间做局部评分排序
重要说明：当前工具不是线性规划、整数规划或机器学习模型；它更接近一个面向制造业务的可解释启发式调度引擎。
通俗理解：
可以把系统想象成一个三层判断器：
第一层看规则合不合法；
第二层看这组订单离目标 MOQ 够不够近；
第三层如果两个系统都能做，再比较谁更合适。

8. 评分取胜的具体例子

下面这个例子可以帮助理解：同一个订单目标相同、两个系统都能做时，系统是如何靠评分而不是靠直觉来做选择的。

案例：订单 2998979332
实际结果：Target = 2.2，最终分配到 GSS3。

该订单在当前规则下，GSS1 + GSS2 和 GSS3 都是合法候选系统。
于是系统进入评分比较，而不是直接按“谁先出现就用谁”。
候选系统评分元组解释
GSS1 + GSS2 (0, 1, 0, 0, 2.2) 不超限，但属于 GSS1+GSS2 做小批次，所以会吃一个 gss12_small = 1 的惩罚。
GSS3 (0, 0, 1, 0, 0.0) 不超限，且 GSS3 做 2.2 是标准场景，因此 gss12_small = 0。
比较顺序：
overflow → gss12_small → priority → usage → closest
为什么最后选 GSS3？
两个系统在第一位 overflow 都是 0，打平；
到第二位 gss12_small 时：
GSS1 + GSS2 = 1，GSS3 = 0。
因为评分是从左到右逐项比较，所以到这里就已经分出胜负，最终 GSS3 取胜。
业务意义：
这个例子说明，系统并不是机械地“永远优先 GSS1 + GSS2”，而是会考虑：
在满足业务规则的前提下，谁更适合做这一个目标批次。
对 2.2 小批来说，GSS3 往往是更自然、更合理的承接系统。

9. 报表与可解释输出

系统输出不仅有结果，还有过程解释，支持培训、审计与业务确认。

  • Orders：逐单结果，包括分配系统、批次、备注、告警、Decision Explain
  • Batches：按系统 × 日期 × 班次统计真实物理批次数
  • Alerts：按统一格式输出超限与异常
  • Summary Tables：按 System / Line / Seg 多维汇总真实批次数
Decision Explain 示例：
Target=2.2; Load=2.237; Pref=[2.120,2.280]; Hard=[1.900,2.500]; Hit=IN_PREFERRED; Score(overflow=0,gss12_small=0,priority=1,usage=1,closest=0.000); System=GSS3
