# GSS3 奇数倍批次拆分：装桶逻辑修正（Spec）

> 由 `writing-spec` 技能产出。这是该功能「系统当前应有样子」的单一真相。
> 改本规范走 `changes/` 提案流程，不直接改。

**状态：** 草稿
**日期：** 2026-07-06
**关联计划：** plans/2026-07-06-gss3-odd-split-bucketing.md

## 1. 目标与背景

**目标：** 修正 `_distribute_orders_to_buckets`，让"把 GSS3 上的 2.2 奇数倍批次（6.6/11.0）拆成 4.4(GSS1+2)×n + 2.2(GSS3)"的既有自愈机制在**批次含已拆分段**时也能成功，避免负载堆在小容量的 GSS3 上导致缸数爆、超班次上限。

**背景（真实案例，2026-07-09 N 班 / HPHRPACK）：**
- 订单 3344736029（2.31 MSU）+ 订单 3375830548（8.782 MSU，上游已拆成 4.4 + 4.4 两段）被搭成一个 **Target=11.0** 的批，落到 **GSS3**（唯一能做 11.0 的系统），在 GSS3 上=5 个 2.2 小缸，**挤爆 GSS3 N 班上限（5→8）**。
- 同班 **GSS1+2 仅用 7/10，有充足空余**。
- 系统本有 `_split_gss3_odd_multiple_batches` 意图把该 11.0 批拆成 4.4(GSS1+2)+4.4(GSS1+2)+2.2(GSS3)（3 缸，负载回到空闲的 GSS1+2），但它调用的 `_distribute_orders_to_buckets` **静默返回 None**：零头单 2.31（起始时间最早）先占了第 0 个 4.4 桶，导致紧随其后的、**已是拆分段（segment_total=2）的 4.4 段**需要横跨桶边界再拆；函数为避免嵌套拆分而 `return None`，整个自愈放弃。

## 2. 范围

- **做什么：** 修改 `BatchManagementTool/src/logic.py` 中的 `_distribute_orders_to_buckets`，使其在装桶时**优先把不可再拆的整段（segment_total > 1）放进目标尺寸匹配的桶**，再按现有时间顺序逻辑填充其余可拆订单。
- **明确不做什么（YAGNI 边界）：**
  - 不改 `_plan_batches_for_group` 的搭批/目标选择逻辑（不动 11.0 目标为何产生）。
  - 不改 `_split_gss3_odd_multiple_batches` 的候选判定、产能检查、n12 计算。
  - 不改 `_rebalance_overflow_batches`、`_second_pass_merge_batches`、系统评分 `_system_score_tuple`。
  - 不改容差、MOQ、系统规格等参数。
  - 不引入按需求大小全局重排（FFD）等更大改动。

## 3. 需求

可验证条目：

- **R1（核心修复）：** 当传入 `_distribute_orders_to_buckets` 的一批订单里含"已拆分段"（`segment_total > 1`）时，该段必须被整段放入某个**目标尺寸与其需求在硬容差内匹配**的桶，不得被要求二次拆分。
- **R2（回归案例）：** 对上述真实案例的输入（批订单 = [2.31, 4.4段, 4.4段]，`bucket_targets = [4.4, 4.4, 2.2]`），函数返回的分桶必须为：两个 4.4 桶各含一个 4.4 段、2.2 桶含 2.31 单；不得返回 None。
- **R3（不可拆段无处安放才失败）：** 仅当某个 `segment_total > 1` 的段找不到任何尺寸匹配且有空间的桶时，才返回 None（保持"放弃拆分、维持原批"的安全行为）。
- **R4（行为保持）：** 当传入批次**不含**已拆分段时，函数行为与修改前**等价**（同样的分桶结果），即新逻辑对旧的成功路径零影响。
- **R5（可拆订单仍按原逻辑）：** 其余 `segment_total <= 1` 的订单继续按现有"时间顺序、跨桶时拆分、拆分结果同步进 `global_orders`"的逻辑填充剩余桶空间。
- **R6（端到端）：** 用 2026-07-06 数据（`--date 20260706`）跑完整流程后，订单 3375830548 的两段 4.4 应分配到 **GSS1 + GSS2**，2.31 单在 GSS3；不再出现 Target=11.0 的 GSS3 批。

## 4. 数据流与组件

**受影响单元（仅一个函数）：** `_distribute_orders_to_buckets(batch_orders, bucket_targets, global_orders)`

**修改后算法（两阶段）：**
1. **阶段一 — 安置不可拆段：** 遍历 `batch_orders` 中 `segment_total > 1` 的订单；为每个段找到第一个"目标在其需求硬容差内、且剩余空间足够"的桶，整段放入并累加该桶负载。找不到 → 返回 None（R3）。
2. **阶段二 — 时间顺序填充其余：** 对剩下的 `segment_total <= 1` 订单，按 `start_datetime` 排序，沿用现有逻辑逐桶填充：能整放则放；跨桶边界则拆分（`_make_order_split`），并把拆分结果同步回 `global_orders`；末桶不得再溢出、空桶视为拆分无意义返回 None。

**调用链（不变）：** `_create_and_assign_batches` → `_split_gss3_odd_multiple_batches` → `_distribute_orders_to_buckets`。

**关键不变量：** 各桶最终非空；各桶负载在其目标的硬容差内；拆分只发生在 `segment_total <= 1` 的订单上；阶段一放入的段与桶目标尺寸匹配（4.4 段进 4.4 桶、2.2 段进 2.2 桶）。

## 5. 安全考量

- **信任边界：** 无新增。函数处理的是已加载、已校验的内部 `ProductionOrder` 对象，不接触外部输入、文件、网络、命令、SQL。
- **敏感数据：** 无（生产计划批次量，无凭据/PII）。
- **特权动作：** 无。
- **滥用场景：** 无外部攻击面；风险仅为"计算错误导致排批不合理"，由 R1–R6 的测试与端到端验证覆盖。
- **对应 MUST/NEVER：** 纯内部计算，`.github/instructions/` 的注入/鉴权/机密类规则不适用；遵守铁律第 12 条"不静默吞错"——本修复正是消除一处静默 `return None` 造成的自愈失效（改为仅在真正无解时才 None）。
